# Hermes — MCP Auth Broker

**Status:** Draft
**Date:** 2026-04-09
**Author:** Tim Schwarz (with Claude)

## Problem

Every MCP server in the fleet that authenticates against a corporate SSO, OAuth, or browser-session service implements its own auth stack. Each one solves the same hard problems — token acquisition, refresh, storage, concurrency, Conditional Access bypass — independently, and each one has slightly different bugs. The result is an unreliable fleet where "auth is broken again" is a recurring daily cost.

The MCPs generated by `thesun` inherit the same fragile per-MCP auth patterns. Fixing MCPs individually does not scale and does not solve the underlying architectural flaw.

### The hard constraint

Corporate SSO with Conditional Access policies (Azure AD device-cert-bound) **cannot be completed inside a container**. Device certificates live on the host. No amount of code quality work fixes this. The authentication flow must execute on the host; containers must read the resulting tokens.

### Observed failure modes

Audit of the current fleet (2026-04-09) identified the following recurring failures:

- **MS365:** Container attempts in-container Firefox headless auth on token expiry. Fails on stale profile locks, missing DISPLAY, and Conditional Access. Silent empty API responses hide the failure.
- **ServiceNow:** Hardcoded 4-hour TTL assumption; REST API session activation can fail silently.
- **CrowdStrike:** CSRF tokens go stale mid-session; no refresh mechanism.
- **Azure DevOps:** ROPC flow breaks when Conditional Access requires interactive MFA; concurrent 401s race.
- **Copilot Studio:** 8-hour cache with zero refresh capability.
- **thesun generator:** OAuth refresh is a stub; HAR interactive login throws "not implemented"; device code flow is missing; no concurrent 401 mutex in any emitted code.
- **thesun / mcp-forge:** Duplicate diverging codebases with the same auth modules copy-pasted.

## Goals

1. Auth across all MCPs should be **as reliable as a standard OAuth client-credentials grant against a public API.** "It just works" after initial setup.
2. A new service requiring any supported auth scheme can be onboarded without writing new auth plumbing.
3. Existing broken MCPs can migrate incrementally without a big-bang rewrite.
4. Cross-platform from day one (macOS, Linux, Windows). No macOS-specific correctness dependencies.
5. Easy deployment for other users: one `npm install`, one config entry, one init command.

## Non-goals

- **Smart auth scheme detection** (probing services to auto-infer their auth flow). Nice to have, but not required for the foundation. Auth type stays explicit in provider config for v1.
- **Credential sharing across machines.** Hermes is a local broker. Multi-machine sync is out of scope.
- **Replacing existing secret stores** (thv, Azure Key Vault, keychain). Hermes uses them; it does not replace them.
- **Human-in-the-loop MFA approval UI.** Push MFA that requires user tap in Authenticator stays manual for v1. TOTP and device-cert flows are handled.

## Architecture

### Overview

Hermes is a **local MCP server** written in Node.js. When an MCP client (Claude Code, Copilot, etc.) loads it, the Hermes process starts. While running, it exposes two interfaces:

1. **MCP tools** over stdio — for humans and agents to inspect state, force refreshes, register services, tail logs.
2. **Local HTTP API** on `127.0.0.1:<port>` — for container MCPs to fetch tokens.

Container MCPs never perform browser auth. They make a single HTTP request to Hermes and receive a validated, current token.

```
┌──────────────────────────────────────┐
```

### Components

#### 1. Hermes broker (`@hermes/broker`)

Long-running Node.js process. Runs on the host. Owns all auth state.

**Internal modules:**

- **`mcp-server.ts`** — MCP server exposing management tools over stdio
- **`http-server.ts`** — Local HTTP API bound to `127.0.0.1` for container consumption
- **`scheduler.ts`** — Proactive refresh loop; refreshes tokens before expiry based on their actual `exp` claim, not TTL guesses
- **`validator.ts`** — Post-cache validation via lightweight test API call per provider, before returning a cached token
- **`mutex.ts`** — Per-service async mutex; prevents concurrent re-auth thundering herd on parallel 401s
- **`storage.ts`** — Cross-platform credential vault using [keytar](https://github.com/atom/node-keytar) (macOS Keychain, Windows Credential Manager, Linux libsecret)
- **`logger.ts`** — Structured logging (JSON lines) to `~/.hermes/logs/`
- **`providers/`** — Pluggable auth providers (see below)
- **`cli.ts`** — CLI commands: `init`, `start`, `status`, `logs`, `register`, `provider list`

#### 2. Provider interface

Every auth scheme is a Provider module. Providers are the extension point.

```typescript
interface Provider {
  name: string;                                // e.g. "ms365", "servicenow"
  schemes: AuthScheme[];                       // sub-tokens this provider can issue
  acquire(ctx: ProviderContext): Promise<TokenBundle>;
  refresh(ctx: ProviderContext, bundle: TokenBundle): Promise<TokenBundle>;
  validate(ctx: ProviderContext, bundle: TokenBundle): Promise<boolean>;
  nextRefreshAt(bundle: TokenBundle): Date;
  dispose?(): Promise<void>;                   // cleanup on broker shutdown
}
```

**Provider contract guarantees:**

- `acquire` performs full login flow. Assumes host has whatever credentials/certs it needs.
- `refresh` attempts silent refresh (refresh-token grant, cookie re-warm, etc.). MUST return a clear "cannot refresh, need full acquire" signal rather than falling back silently.
- `validate` MUST make a real API call. Cache-TTL checks alone are a known failure mode — the broker explicitly does not trust them.
- `nextRefreshAt` reads actual token expiry claims. Default policy: refresh at `exp - 20%` of total lifetime, minimum 5 minutes before expiry.
- `dispose` cleans up browser profiles, temp files, etc.

**Built-in providers for v1:**

| Provider | Use case |
|---|---|
| `ms365` | Microsoft 365 Graph, Teams, Outlook (wraps existing `host-auth.mjs`) |
| `azure-ad-sso` | Generic Azure AD browser SSO (ServiceNow, Copilot Studio, etc.) |
| `oauth2-authz-code` | Standard OAuth2 authorization code + refresh token |
| `oauth2-device-code` | OAuth2 device flow (for headless/TV-style auth) |
| `oauth2-client-credentials` | Machine-to-machine OAuth2 |
| `basic-auth` | HTTP Basic / static API key |
| `cookie-session` | Generic Playwright browser capture with HAR export |

Providers can ship as part of Hermes core or as separate npm packages (`@hermes/provider-<name>`). Third-party providers are supported.

#### 3. Client library (`@hermes/client`)

Thin npm package that container MCPs import. Single primary API:

```typescript
import { HermesClient } from '@hermes/client';

const auth = new HermesClient({
  brokerUrl: process.env.HERMES_URL ?? 'http://host.docker.internal:9876',
});

// Fetch a token
const token = await auth.getToken('ms365', 'graph');

// Authorize outgoing requests
const headers = await auth.authHeaders('ms365', 'graph');
```

**Client guarantees:**

- Retries with exponential backoff on broker unavailability (configurable; default 3 retries over 5s)
- Local in-process cache with a short TTL (default 30s) to avoid hammering the broker on request bursts
- Surfaces broker errors loudly — throws `HermesError` with a specific `code` field. **Never returns empty/null on auth failure.** (The MS365 silent-empty-results bug is explicitly what this prevents.)
- Honors a per-service in-flight mutex so concurrent requests for the same token dedupe

#### 4. thesun integration

thesun is refactored so it no longer inlines auth code into generated MCPs. New generation flow:

1. User specifies (or thesun detects from patterns) that the target service requires `auth_type: X`.
2. thesun checks if a Hermes provider for `X` exists.
3. If yes: generates container code using `@hermes/client`. Optionally generates a Hermes config file registering the service.
4. If no: generates a **new Hermes provider module** (not inlined auth in the MCP). The new provider is installed into the user's Hermes broker.

The existing `azure-ad-sso-auth.ts` implementation in thesun (the one part that actually works) is extracted and becomes the basis for `providers/azure-ad-sso.ts` in Hermes. No battle-tested code is lost — it moves to a better home.

### HTTP API

Minimal surface, bound to `127.0.0.1` only. Token authentication via a shared secret generated on broker init and written to `~/.hermes/client.token` (mode 0600). Containers bind-mount the token file or read it via env.

```
GET  /health                          → broker health
GET  /token/:service/:scheme          → current token (JSON)
GET  /token/:service/:scheme?force=1  → force refresh, then return
POST /refresh/:service                → trigger refresh for all schemes of a service
GET  /status                          → full fleet status
```

All requests require `Authorization: Bearer <client-token>` header. No CORS. Not reachable outside localhost.

### MCP tools (management interface)

Exposed to the MCP client for human/agent debugging and management:

| Tool | Purpose |
|---|---|
| `hermes_status` | Show all services, token state, next refresh, recent errors |
| `hermes_force_refresh` | Force refresh for a service (bypasses cache) |
| `hermes_register_service` | Register a new service with an existing provider |
| `hermes_list_providers` | List installed providers and their capabilities |
| `hermes_install_provider` | Install a new provider from npm |
| `hermes_tail_logs` | Return recent structured log lines |
| `hermes_acquire` | Trigger full acquire flow (browser login) for initial setup |
| `hermes_diagnose` | Run a diagnostic pass — validates every service, reports failures |

### Storage layout

```
~/.hermes/
├── config.json              # broker config, port, logging level
├── services.json            # registered services with provider bindings
├── client.token             # shared secret for HTTP API (mode 0600)
├── logs/
│   └── hermes-YYYY-MM-DD.jsonl
└── providers/               # installed third-party providers
    └── @hermes/provider-foo/
```

Secrets (tokens, refresh tokens, cookies, passwords) are **never** stored in plain files. Storage goes through keytar.

### Concurrency model

Every token fetch for a given `(service, scheme)` goes through a per-key async mutex. On 401 from a downstream service, multiple parallel requests coalesce into a single refresh attempt; all waiters receive the same new token. This directly fixes the concurrent-401 thundering herd identified in the audit.

The scheduler operates independently of request flow. When the scheduler decides to refresh, it acquires the same mutex — so scheduler-driven and request-driven refreshes can never collide.

### Validation policy

When a token is requested, the broker:

1. Checks if a cached bundle exists.
2. If cached and `now < exp - safety_margin`, runs `validate()` on a configurable policy:
   - **Eager** (default): validate on every request older than 60s cache
   - **Lazy**: trust TTL, only validate when request fails
   - **Paranoid**: validate every request
3. If validation fails, attempts `refresh()`.
4. If refresh fails or returns `NEEDS_ACQUIRE`, attempts `acquire()`.
5. If acquire fails, returns `HermesError` with a clear remediation hint (e.g., "run `hermes_acquire ms365` to complete interactive login").

This replaces the TTL-only caching that caused "cached but actually invalid" failures across the fleet.

## Deployment

### For the author (Tim)

```bash
npm install -g @yourname/hermes
hermes init                   # sets up ~/.hermes/, generates client token
hermes provider install @hermes/provider-ms365
hermes acquire ms365          # interactive first-time login
```

Add one entry to `~/.claude/user-mcps.json`:

```json
{
  "hermes": {
    "command": "hermes",
    "args": ["start", "--stdio"]
  }
}
```

That is the complete setup.

### For other users (cross-platform)

Same install. Hermes has no macOS-specific correctness dependencies:

- **Runtime:** Node.js (cross-platform)
- **Credential storage:** keytar (macOS Keychain, Windows Credential Manager, Linux libsecret via `libsecret-1-dev`)
- **Browser automation:** Playwright (cross-platform)

**Auto-start** (optional, platform-specific convenience wrappers):

- macOS: `hermes install-autostart` writes a LaunchAgent plist
- Linux: `hermes install-autostart` writes a systemd user unit
- Windows: `hermes install-autostart` writes a Task Scheduler entry

Auto-start is a convenience, not a requirement. Hermes is fully functional when started on demand by the MCP client.

## Phased delivery

### Phase 0 — Kill duplication

Decide between `thesun` and `mcp-forge`. Pick one. Delete the other. This is a prerequisite for any further refactor — diverging duplicate auth code blocks clean extraction.

**Deliverable:** one generator repo, clean history.

### Phase 1 — Broker shell + ms365 provider

Build the broker core (MCP server, HTTP server, storage, mutex, scheduler, validator, logger). Implement the `ms365` provider by extracting and cleaning up the existing `host-auth.mjs` logic. Build the client library. Migrate `ms365-mcp` container to use the client library. Remove in-container Firefox from ms365-mcp Dockerfile.

**Deliverable:** ms365 auth is reliable. No more "empty API responses" failures. Tokens refresh proactively. This alone eliminates most of the day-to-day pain.

### Phase 2 — Additional providers and fleet migration

Implement providers in priority order:

1. `azure-ad-sso` (generic — unlocks ServiceNow, Copilot Studio, generic corporate services)
2. `oauth2-authz-code` with real refresh (fixes thesun's stub)
3. `oauth2-device-code` (new — was missing entirely)
4. `cookie-session` with Playwright HAR capture (fixes thesun's stub)
5. `basic-auth` / `api-key` (simple)
6. `oauth2-client-credentials` (machine-to-machine)

Migrate existing MCPs to the client library one at a time: servicenow, crowdstrike, copilot-studio, azure-devops.

**Deliverable:** full fleet on Hermes. All the recurring auth pain from the audit is fixed at the broker level.

### Phase 3 — thesun refactor

Rewrite thesun's auth code generation so it:

- Detects required auth type (from explicit config or patterns)
- Checks for a matching Hermes provider
- Generates client-library-based MCPs, not inlined auth
- When a new provider is needed, generates it as a Hermes provider module and installs it

Extract thesun's `azure-ad-sso-auth.ts` implementation into `@hermes/provider-azure-ad-sso`.

**Deliverable:** new MCPs generated by thesun are born reliable. The generation pipeline no longer inlines auth complexity per MCP.

### Phase 4 — Polish

- Auto-start wrappers for each OS
- `hermes_diagnose` comprehensive health check
- Observability dashboard (rendered via MCP tool output)
- Third-party provider registry / marketplace conventions
- Public documentation for external users

**Deliverable:** product-quality release usable by people other than the author.

## Risks

- **Playwright fragility.** Browser automation depends on stable HTML selectors in Microsoft login forms. Mitigation: fail loud on selector miss (do not return cached/empty data), centralize selector logic in the `azure-ad-sso` provider so one fix updates all consumers.
- **keytar dependency friction on Linux.** libsecret requires a running secret service (gnome-keyring or similar). Mitigation: document clearly; provide a file-backed encrypted fallback (AES-256-GCM with a passphrase-derived key) for headless Linux.
- **Provider interface churn.** Breaking the provider interface breaks third-party providers. Mitigation: version the interface, support both major versions during transitions.
- **Broker as single point of failure.** If Hermes crashes, all MCPs lose auth. Mitigation: structured logging, crash-loop detection, MCP tool `hermes_status` for fast diagnosis, keep state on disk so restart is fast.
- **Credentials theft surface.** Local HTTP API + shared secret is weaker than Unix sockets. Mitigation for v1: bind to 127.0.0.1, require bearer token, log all requests. For v2, consider Unix socket on macOS/Linux and named pipe on Windows.

## Open questions

- Should the broker support multiple MCP clients connecting simultaneously (Claude Code + Copilot + Cursor at the same time)? MCP stdio is 1:1 by default. For v1, accept this limitation — document that Hermes runs from one primary MCP client, all other clients talk to it over HTTP.
- Should thesun's `sun:auth` skill be retired, folded into `hermes_acquire`, or kept as a standalone tool? Leaning toward folding — one way to capture auth tokens, not two.
- Provider distribution: npm registry or a private Hermes-specific registry? Start with npm (simpler).

## Success criteria

Hermes is successful when:

1. The operator has not manually re-authenticated an MCP in 30 days.
2. A new corporate service can be onboarded in under 15 minutes without writing any auth code.
3. No MCP in the fleet silently returns empty responses on auth failure. All auth failures surface with actionable errors.
4. A fresh clone + install on Linux or Windows produces a working broker without platform-specific fixups.
5. `thesun` generates new MCPs that use Hermes by default; auth is not a separate concern for generated MCPs.
